## 에이전트

**0~4 는 오케스트레이터가 준비하고, 5~8 을 에이전트가 맡고, 9 에서 결과를 전달한다.**
아래 `## 0.` ~ `## 9.` 절 번호와 같다.

네 에이전트는 각자 **앞 단계의 산출물을 입력으로 받고, 자기 산출물을 직접 쓴다.**

| 에이전트 | 역할 |
|---|---|
| `legacy-analyzer` | 진단 — 무엇이 문제인지 찾는다 |
| `refactoring-strategist` | 전략 — 작업으로 묶고 순서를 정한다 |
| `refactoring-engineer` | 실행 — 작업 하나씩 반영한 코드를 만든다 |
| `modernization-reviewer` | 검토 — 단계 사이 어긋남을 찾는다 |

## 표기

**약자를 쓰지 않는다.** 읽는 사람이 무슨 뜻인지 찾아보게 만들지 않는다.

| 표기 | 의미 |
|---|---|
| `항목-01` | 진단이 찾은 문제 하나 |
| `작업-01` | 항목을 묶어 만든 실행 단위 |
| `39줄` | 위치. **항상 원본 기준** |

`00`~`04` 는 `_workspace/` 산출물을 번호로 줄여 부르는 것이다.

## 결과물
각 에이전트들의 출력물들은 `_workspace/` 에 남긴다.

```
_workspace/00_input.md                  ← 1~4 단계 (준비)
_workspace/01_legacy_analysis.md        ← 5 단계   (진단)
_workspace/02_refactoring_strategy.md   ← 6 단계   (전략)
_workspace/03_migration_plan.md         ← 7 단계   (실행 기록)
_workspace/output/{원본 경로}           ← 7 단계   (리팩토링 결과물)
_workspace/04_review_report.md          ← 8 단계   (검토)
```

**한 번 호출하면 끝까지 간다. 중간에 묻지 않는다.**
1 단계의 중단 조건(대상을 못 찾음 등)과 작업 실패 외에는 멈추지 않는다.

**대상 파일 하나를 진단하는 작업이다. 프로젝트를 훑지 않는다.**

| 주체 | 읽는 것 |
|---|---|
| 오케스트레이터 | `composer.json` (또는 `pyproject.toml`), lock 파일은 **Grep 만**, 설정 파일 존재 확인 |
| legacy-analyzer | **대상 파일**, `00_input.md`, 근거로 지정된 설정 파일 |
| refactoring-strategist | `00_input.md`, `01_legacy_analysis.md` — **대상 파일도 열지 않는다** |
| refactoring-engineer | `00_input.md`, `02_refactoring_strategy.md`, **대상 파일** |
| modernization-reviewer | `_workspace/` 산출물 전부 (`output/` 결과물 포함). 원본은 대조가 필요할 때만 |

여기에 없는 파일은 열지 않는다. `.gitignore` 에 있는 것도 열지 않는다.

**어떤 단계에서도 프로젝트의 기존 파일을 덮어쓰지 않는다.**
결과물은 `_workspace/output/` 에 새로 만들고, 적용은 사용자가 한다.

## 0. 이어하기 판정 — 있는 것은 다시 만들지 않는다

**1 단계로 가기 전에 `_workspace/` 를 먼저 본다.** 산출물이 이미 있으면 그 다음 단계부터 시작한다.

**재사용 전에 대상이 같은지 확인한다.** `00_input.md` 의 `대상` 이 지금 지정한 경로와 다르면
재사용하지 않고 1 단계부터 다시 한다. 다른 파일의 계획서로 작업할 수는 없다.

### 다시 만들라고 하면 다시 만든다

사용자가 `새로`, `다시`, `--new` 등으로 재생성을 요청하면 해당 단계부터 새로 만든다.

```
/refactor <파일> 새로          → 1 단계부터 전부
/refactor <파일> 02만 다시      → 6 단계부터 (01 은 그대로)
```

---

## 1. 대상을 받는다

호출할 때 받은 인자가 분석 **대상**이다. 파일 경로일 수도, 디렉토리일 수도 있다.

- 경로가 주어졌다 → 실재하는지 확인하고 그것만 대상으로 한다
- 파일명만 주어졌다 → Glob 으로 찾는다.
  후보가 여러 개면 목록을 보여주고 사용자가 고르게 한다. **임의로 고르지 않는다**
- 못 찾았다 → **거기서 멈춘다.** 비슷한 이름으로 추측해서 진행하지 않는다
- 인자가 없다 → **전체를 스캔하지 말고 먼저 물어본다.**
  "어떤 파일을 볼까요?" 전체 분석은 사용자가 명시적으로 "전체" 라고 했을 때만 한다

## 2. 스택과 파일 종류를 판정한다

먼저 언어와 프레임워크를 정한다.

| 판정 | 근거 |
|---|---|
| 언어 | 대상 파일 확장자 (`.php` / `.py`) |
| 프레임워크 | `composer.json` + `artisan` / `pyproject.toml` + FastAPI import |

그다음 **파일 종류**를 본다. 종류마다 볼 것이 다르다.

| 경로 / 확장자 | 종류 | 관심사 |
|---|---|---|
| `app/Services/*.php`, `app/Models/*.php` | 순수 PHP 클래스 | 클래스 설계, 의존성, 책임 분리 |
| `app/Http/Controllers/*.php` | 컨트롤러 | 비즈니스 로직 유출, 요청 검증 위치 |
| `*.blade.php` | Blade 뷰 | 로직이 뷰에 새어들어왔는지 |
| `routes/*.php` | 라우트 정의 | 라우트 구조, 미들웨어 |
| `database/migrations/*.php` | 마이그레이션 | **대상에서 제외한다** |
| `app/routers/*.py` | FastAPI 라우터 | 핸들러 비대화, 의존성 주입 |
| `app/schemas/*.py` | Pydantic 스키마 | 검증 책임 위치 |
| `alembic/versions/*.py` | 마이그레이션 | **대상에서 제외한다** |

## 3. 근거와 제약을 모은다

### 런타임 제약 — 천장을 먼저 읽는다

`composer.json` 의 `require.php` / `pyproject.toml` 의 `requires-python` 에 선언된
**하한**이 곧 상한이다. `^7.3` 은 "7.3 에서도 돌아야 한다" 는 뜻이므로,
실제 서버가 더 높더라도 보수적으로 잡는 쪽이 안전하다.

**선언만 믿지 않는다.** 설치된 패키지가 더 높은 버전을 요구하면 실제 하한이 올라간다.

```
composer.json                 php: ^7.3|^8.0     → 7.3 처럼 보이지만
elasticsearch/elasticsearch   php: ^7.4 || ^8.0  → 실제 하한은 7.4
```

```
Grep  패턴: "php":     파일: composer.lock
```

나온 값 중 **가장 높은 하한**을 확정 하한으로 삼는다.
Python 은 `uv.lock` / `poetry.lock` 에 같은 방식.

lock 파일이 없으면 선언값을 쓰되 `00_input.md` 에 **"lock 미확인"** 을 적는다.

**패키지별 표를 만들지 않는다.** `00_input.md` 에는 확정 하한 한 줄과
그 근거가 된 제약값 하나면 충분하다.

```markdown
- 확정 하한: PHP 7.4
  (composer.json 은 ^7.3|^8.0 이나, lock 에 ^7.4 || ^8.0 요구 패키지 존재)
```

### 확정된 하한 기준으로 제외 목록을 만든다

**그보다 나중에 도입된 문법만** 제외한다. 하한을 낮게 잡으면 쓸 수 있는 문법을 못 쓰게 된다.

| 문법 | 도입 |
|---|---|
| arrow function `fn() =>`, typed property, `??=` | 7.4 |
| 생성자 프로퍼티 승격 `__construct(private Repo $r)` | 8.0 |
| `match` 식, nullsafe `?->`, named arguments, `str_contains()` | 8.0 |
| `enum` | 8.1 |
| `readonly` | 8.2 |

`00_input.md` 에는 **제외 목록만** 적는다. "사용 가능한 것" 과 섞어 쓰지 않는다 — 읽는 쪽이 헷갈린다.

문법뿐 아니라 프레임워크도 같다. 상한이 N 이면 **N+1 부터 들어온 헬퍼·API 를 제외한다.**

### 근거 — 있는 것만 모은다

우선순위대로 **실재하는 것만** 목록에 넣는다.

| 순위 | 근거 |
|---|---|
| 1 | 프로젝트 설정 파일 — `phpstan.neon`, `.editorconfig`, `pyproject.toml` |
| 2 | 컨벤션 문서 — `docs/conventions/*.md`, 프로젝트 `CLAUDE.md` |
| 4 | 언어·프레임워크 표준 — 스타일 규격, 프레임워크 관례 |

**3순위(주변 코드)는 목록에 넣지 않는다.** analyzer 는 대상 파일 하나만 읽는다.
주변 파일을 근거로 적어두면 그것들을 열러 가고, 파일 하나 보는 데 프로젝트 전체를 훑게 된다.

설정 파일을 목록에 올릴 때는 **그 파일에서 읽은 값을 그대로 옆에 적는다.**
`preset: {이름}` 처럼 이름만 있고 규칙 내용이 없으면 **`(프리셋 — 세부 규칙 없음)`** 이라고 덧붙인다.
그래야 analyzer 가 프리셋 내용을 그 파일의 규정으로 착각하지 않는다.

```markdown
- [1순위] `.editorconfig` — 스페이스 4칸, LF, UTF-8, 파일 끝 개행
- [1순위] `{설정 파일}` — preset `{이름}` **(프리셋 — 세부 규칙 없음)**, `{규칙}` 비활성
```

**설정 파일은 읽기만 한다.** Pint / PHPStan / Ruff / mypy 를 설치하거나 실행하지 않는다.

## 4. `_workspace/00_input.md` 를 쓴다

`_workspace/` 는 **지금 작업 중인 프로젝트**(현재 디렉토리) 에 만든다.

```markdown
# 분석 입력

- 대상: {대상 파일 경로}
- 종류: {2 단계 표에서 판정한 종류}
- 관심사: {같은 표의 관심사를 그대로 옮긴다}
- 스택: {언어} / {프레임워크}

## 런타임 제약
- 확정 하한: {언어} {버전}
  ({선언 파일} 은 {선언값} 이나, lock 에 {더 높은 제약} 요구 패키지 존재)
- {프레임워크}: {버전}
- 위 상한을 넘는 문법·API 는 제안하지 않는다

## 제외 목록
| 문법 | 도입 |
| {상한보다 나중에 도입된 문법} | {버전} |

## 사용 가능한 근거
- [1순위] `.editorconfig` — {읽은 값}
- [2순위] {컨벤션 문서 경로}
- [4순위] {언어·프레임워크 표준}

## 사용자 요청 원문
"{사용자가 친 그대로}"
```

없는 근거는 **없다고 적는다.** 빈칸으로 두지 않는다.

## 5~8. 에이전트를 순서대로 띄운다

`00_input.md` 를 쓴 직후 바로 시작한다. 각 에이전트는 산출물을 **직접 쓰고 요약만 돌려준다.**

| 단계 | 에이전트 | 넘기는 것 | 산출물 |
|---|---|---|---|
| 5 | legacy-analyzer | 대상 경로 / 종류·관심사 / 확정 하한 / `00` 을 읽으라는 지시 | `01` |
| 6 | refactoring-strategist | 대상 경로 / `00`·`01` 을 읽으라는 지시 | `02` |
| 7 | refactoring-engineer | **작업 ID 하나** / 대상 경로 / `00`·`02` 를 읽으라는 지시 | `03` + `_workspace/output/` |
| 8 | modernization-reviewer | `_workspace/` 를 읽으라는 지시 | `04` |

### 넘기면 안 되는 것 — 전 단계 공통

| 금지 | 이유 |
|---|---|
| 대상 파일의 내용, 앞 단계 **요약** | 각자 원본을 직접 읽는다. 요약을 주면 항목 ID 와 위치가 빠진 채로 판단한다 |
| 미리 찾아둔 문제·작업·순서, 어디를 보라는 지시 | **그게 그 에이전트가 할 일이다.** 받아쓴 것은 근거 추적이 안 된다 |

**산출물 본문을 읽지 않는다.** 확인하겠다고 Read 하면 절약한 만큼을 도로 쓴다.
파일이 생겼는지만 확인한다.

### 7 단계 — 작업 반복

계획서의 작업을 순서대로 하나씩 실행한다. `03` 에 이미 기록된 작업은 건너뛴다.
engineer 는 한 번에 **작업 하나**만 받고, 하나가 끝나면 다음 것을 바로 띄운다.
결과물이 `_workspace/output/` 에 누적되므로 앞 작업 결과 위에 얹힌다.

`/refactor <파일> 작업-03까지` 처럼 범위를 주면 그만큼만, 지정이 없으면 **전부** 실행한다.
작업이 실패해 중단됐어도 **8 단계는 거기까지 만들어진 것을 검토한다.**

## 9. 결과를 전달한다

**원본은 수정되지 않았다.** 결과물은 `_workspace/output/` 에 있다. 이 사실을 먼저 알린다.

- 실행한 작업 (작업-01~작업-03 처럼 범위로)
- 결과물 경로 — `_workspace/output/` 을 떼면 그대로 적용 경로다
- **`X` 로 표시된 작업** — 몇 건인지, 무엇이 계획과 달랐는지 한 줄로 (`04` 의 `1` 절)
- **적용 전에 돌려볼 것** — `04` 의 `2` 절 그대로
- **확인해야 할 점** — `04` 의 `3` 절 그대로. 답을 받으면 다음 라운드에서 작업이 된다

**런타임 상한을 넘는 문법이 결과물에 있으면 적용하지 말라고 분명히 말한다.**
그대로 복사하면 코드가 깨진다.

그다음 적용 방법을 안내한다. **복사는 사용자가 한다.**

```
diff -r app/ _workspace/output/app/
```

## 에러 핸들링

| 상황 | 처리 |
|---|---|
| `composer.json` / `pyproject.toml` 없음 | 런타임 제약을 "확인 불가" 로 적고 진행. **버전 관련 제안을 일절 하지 않는다** |
| 근거가 하나도 없음 | 진행하되 `00_input.md` 에 "근거 없음" 을 명시. 1순위 규정 대조를 건너뛰게 됨을 알린다 |
| **산출물이 생기지 않음** | 그 에이전트가 돌려준 사유를 그대로 전달한다. **오케스트레이터가 대신 만들지 않는다** |
| 발견 항목 0 건 | 6 단계부터 건너뛴다. "문제 없음" 을 전달하고 끝낸다 |
| 작업 하나가 실패로 반환 | **거기서 멈춘다.** 남은 작업을 계속하지 않고 어디까지 됐는지 알린다 |
| engineer 가 "계획의 내용을 못 찾음" 으로 반환 | `/refactor <파일> 새로` 로 진단부터 다시 하도록 안내한다 |
