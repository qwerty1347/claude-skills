# 새 스킬 만들기

스킬은 **반복되는 지시를 파일로 굳힌 것**이다. 매번 설명하던 절차를 한 번만 쓰고,
다음부터는 알아서 꺼내 쓰게 한다.

세 번 이상 같은 말을 타이핑했을 때 만든다. 그 전에는 만들지 않는다 —
한 번 하고 말 작업에 스킬을 만들면 관리 대상만 늘어난다.

## Phase 0 — 기존 스킬 점검

`${CLAUDE_SKILL_DIR}/..` (이 스킬이 들어있는 `skills/` 디렉터리)를 먼저 확인한다.
현재 프로젝트에 `.claude/skills/` 가 있으면 그쪽도 본다.

- 같은 일을 하는 스킬이 이미 있으면 → **새로 만들지 말고 기존 것을 고친다**
- 트리거만 안 걸리는 문제면 → Phase 4 로 바로 간다 (description 수정)
- 결과물이 마음에 안 드는 문제면 → Phase 5 로 간다 (본문 수정)

## Phase 1 — 무엇을 고정할지 확인

사용자에게 묻는다.

1. 어떤 작업을 반복하고 있나
2. 지금은 매번 어떻게 지시하나 — **요약 말고 실제 문장 그대로** 받는다
3. 결과물이 어떤 모양이면 성공인가

2번이 Phase 4 의 재료가 된다. 여기서 절차가 흐릿하면 스킬도 흐릿해진다.
구체적인 예시를 최소 1개 확보한 뒤 넘어간다.

## Phase 2 — 이름 정하기

영문 소문자 + 하이픈. 폴더 이름이 그대로 `/명령어` 가 된다.

동사로 짓는다. `review-pr`, `write-post` 는 뭘 하는지 보이지만
`pr`, `post` 는 안 보인다.

## Phase 3 — 어디에 둘지 정하고 파일 생성

먼저 범위를 정한다. 기준은 하나다 — **다른 프로젝트에서도 쓸 것 같은가.**

| 답 | 위치 | 성격 |
|---|---|---|
| 그렇다 | `${CLAUDE_SKILL_DIR}/../{이름}/SKILL.md` | 전역. 이 저장소에 커밋된다 |
| 아니다 | `${CLAUDE_PROJECT_DIR}/.claude/skills/{이름}/SKILL.md` | 그 프로젝트 전용. 그 저장소에 커밋된다 |

애매하면 **프로젝트 쪽으로 시작한다.** 나중에 다른 데서도 쓰고 싶어지면 그때 전역으로
옮기면 되지만, 전역에 쌓인 프로젝트 전용 스킬은 아무도 정리하지 않는다.

경로를 절대경로로 적지 않는다. 위 두 변수는 Claude Code 가 치환해주며,
저장소를 어디로 옮기든 · 누가 클론하든 그대로 동작한다.

frontmatter 필수 두 줄:

```yaml
---
name: {폴더와 같은 이름}
description: {Phase 4 참고}
---
```

선택 필드와 상세 규칙은 [`references/skill-writing-guide.md`](references/skill-writing-guide.md) 참고.
배포·커밋처럼 Claude 가 알아서 부르면 곤란한 스킬이라면 그 문서의
`disable-model-invocation` 항목을 반드시 확인한다.

## Phase 4 — description 작성

**스킬이 안 불려오는 사고의 대부분은 여기서 난다.** 본문이 아니라 이게 트리거다.

- "무엇을 하는지" + "언제 쓰는지" 둘 다 넣는다
- Phase 1-2 에서 받은 **실제 발화**를 그대로 넣는다. 격식체·반말 전부
- 재실행 표현도 넣는다: "다시", "수정해줘", "업데이트"

```yaml
# 나쁨 — 언제 쓸지가 없다
description: PDF 처리 유틸리티

# 좋음
description: PDF 읽기·텍스트/표 추출·병합·분할·회전·워터마크·암호화·OCR.
  .pdf 파일이 언급되거나 PDF 출력이 필요할 때 사용.
```

작성 패턴이 더 필요하면 [`references/skill-writing-guide.md`](references/skill-writing-guide.md) 를 읽는다.

## Phase 5 — 본문 작성

- **명령형으로.** 설명문이 아니라 지시문이다
- **이유를 적는다.** "항상 X 해라" 보다 "Y 때문에 X 한다" 가 예외 상황에서 잘 작동한다
- **500줄을 넘기지 않는다.** 넘으면 `references/` 로 뺀다
- 좁은 규칙에 과적합시키지 않는다 — 비슷한 변형에도 통해야 한다

폴더에 같이 둘 수 있는 것:

```
{이름}/
├── SKILL.md          ← 필수
├── references/       ← 필요할 때만 읽히는 긴 문서
├── scripts/          ← 매번 다시 짜기 아까운 코드
└── assets/           ← 템플릿, 이미지 등 출력에 쓰는 파일
```

## Phase 6 — 트리거 테스트

**만들고 끝내지 않는다.** 여기까지가 한 세트다.

1. 사용자가 칠 법한 문장 **3개**를 만들어 실제로 불려오는지 확인한다
2. 안 불려오면 → 그 표현을 `description` 에 추가하고 다시 확인
3. 비슷하지만 **불려오면 안 되는** 문장 **2개**로도 확인한다 (과잉 트리거 점검)
4. 불려오는데 결과가 별로면 → description 이 아니라 **본문**의 절차를 고친다

`~/.claude/skills` 가 링크로 연결돼 있으면 저장 즉시 반영된다.
새로 만든 폴더가 인식 안 되면 Claude Code 를 재시작한다.

## Phase 7 — 등록

전역 스킬이면 `${CLAUDE_SKILL_DIR}/../../README.md` 의 스킬 목록 표에 한 줄 추가하고,
같은 위치의 `CHANGELOG.md` 에 날짜와 내용을 기록한다.

프로젝트 전용 스킬이면 그 프로젝트의 `CLAUDE.md` 에 한 줄만 남긴다 —
무엇을 하는 스킬이고 언제 부르는지. 스킬 목록 전체를 옮겨 적지 않는다.
파일 시스템을 보면 알 수 있는 것을 문서에 중복해두면 둘이 어긋난다.

## 하지 말 것

- 스킬 안에서 또 스킬을 부르는 구조 — 절차가 꼬인다
- 프로젝트별 컨벤션을 스킬에 하드코딩 — 그건 그 프로젝트 `CLAUDE.md` 가 할 일
- 만들자마자 다음 스킬로 넘어가기 — 한 개를 쓸 만하게 만드는 게 먼저다
- Phase 6 건너뛰기 — 검증 안 한 스킬은 안 만든 것과 같다
