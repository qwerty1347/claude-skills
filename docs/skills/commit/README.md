# /commit

## 무엇을 하는가

변경 내용을 읽고 Conventional Commits 형식으로 커밋한다. **push 는 하지 않는다.**

## 왜 만들었는가

`git status` 만 보고 메시지를 지으면 `update files` 같은 커밋이 쌓인다.
매번 "diff 를 보고 왜 고쳤는지 쓰라" 고 지시하던 것을 굳혔다.

## 어떻게 쓰는가

`/commit` 으로만 부른다. 말로는 불려오지 않는다.

## 왜 이렇게 만들었는가

| 판단 | 이유 |
|---|---|
| `disable-model-invocation: true` | 커밋은 되돌릴 수 있지만, 다른 작업 끝에 딸려 나가면 안 된다. 부르는 시점을 사람이 정한다 |
| push 를 하지 않음 | 로컬 커밋은 되돌릴 수 있고 push 는 남에게 나간다. 되돌리기 비용이 다른 두 동작을 한 스킬에 묶지 않는다 |
| `scope` 를 쓰지 않음 | 명세상 선택 항목이다. 저장소가 작으면 영역 기준이 흔들려 `feat(api)` · `feat(skill)` 이 제각각이 된다 |
| git 을 Bash 로 고정 | `allowed-tools` 가 `Bash(git ...)` 기준이라 PowerShell 로 돌리면 매번 승인을 묻는다 |
| `BREAKING CHANGE:` 꼬리말 (`feat!:` 아님) | 축약형도 명세상 맞지만, 무엇이 어떻게 깨지는지 한 줄이 남아야 읽는 사람이 조치할 수 있다 |
| `allowed-tools` 를 명령 단위로 나열 | `Bash(git *)` 로 열면 `git push` · `git reset` 까지 열린다 |

## 함정

- **이미 스테이징된 게 있으면 그것만 커밋한다.** 사용자가 의도적으로 고른 범위다.
  전체를 담으면 남의 작업이 섞인다
- **`type` 을 대충 고르기 쉽다.** 문서만 고쳤으면 `feat` 이 아니라 `docs` 다
- **변경이 없으면 멈춘다.** 빈 커밋을 만들지 않는다

## 검증

이 저장소의 커밋 이력이 그대로 검증 결과다. `feat` · `docs` · `chore` 구분,
50자 이내, 마침표 없음 — 형식이 유지되고 있다.

## 제작 기록

`git push` 를 넣을지 고민했지만 뺐다. 넣는 순간 "커밋해줘" 가 되돌릴 수 없는 동작이 된다.
push 가 필요하면 사람이 직접 친다.
